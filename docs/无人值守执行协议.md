# 无人值守执行协议

状态：`accepted_for_planning`
适用范围：`docs/milestones/` 下的 M1～M8 执行规格，以及架构规格第 19 节的跨里程碑 Gate
人工决策入口：[todoe-check.md](../todoe-check.md)

## 1. 目标

本协议约束上下文较小、一次只执行一个任务卡的大语言模型。执行模型只负责完成已派发任务，不负责重排路线、替负责人关闭决策或扩大产品范围。

## 2. 权威顺序

发生冲突时按以下顺序处理：

1. 根 `AGENTS.md`；
2. `项目计划.md` 的产品范围和里程碑定义；
3. `docs/spec/` 的阶段要求；
4. 已接受的 `docs/adr/`；
5. `docs/schemas/` 的机器契约；
6. 对应里程碑执行规格；
7. 当前任务卡。

低层文件不得静默覆盖高层文件。冲突无法通过保持更窄范围解决时，任务结果必须为 `blocked`。

`draft` 状态的架构规格是辅助设计输入，不是独立权威层。其中引用的 accepted ADR、schema 和本协议 Gate 各按上述顺序生效；其余内容只能在与第 1～6 项一致时作为任务输入。

## 3. 无人值守原则

- 派发器可以连续执行所有前置满足且不需要人工决策的任务。
- 任一任务只领取一个任务 ID，不合并相邻任务。
- Decision Gate 关闭前，只允许执行该 Gate 明确列出的任务；通常只放行只读审计、包骨架、Mock 或夹具，范围保护类 Gate 可逐 ID 放行不受该决定影响的实现任务。
- 需要人工确定的事项只能引用根 `todoe-check.md` 的稳定 ID，不在任务内自行选择。
- 单个分支被人工决策阻塞时，派发器继续执行其他无依赖分支。
- 所有可运行分支耗尽后，输出阻塞清单、已完成证据和下一可执行任务，不把部分完成写成里程碑完成。
- 不修改或正式化 `docs/ideas/` 中的内容。

## 4. 任务状态

任务只使用以下状态：

| 状态 | 含义 |
|---|---|
| `pending` | 前置未检查或尚未派发 |
| `ready` | 前置、文件占用和 Gate 均满足 |
| `in_progress` | 已由一个执行者领取 |
| `complete` | 单一结果和全部必测项均有证据 |
| `blocked` | 缺少决策、依赖、环境或上游契约 |
| `failed` | 实现或验证失败，且失败证据已记录 |
| `not_applicable` | 已关闭的条件分支明确排除该任务 |

禁止使用 `done`、`skip`、`mostly_complete` 等同义状态。

里程碑文件头的“当前门禁”只摘要 G00 的上游入口，不列 Decision Gates，也不能作为派发依据。实际派发必须同时检查该文件全部 Gate、任务卡前置、DAG 和文件占用。

## 5. Decision Gate 与人工待办

每个 Gate 必须列出：

- 状态；
- 阻塞的任务；
- 对应 `TODO-Mx-yy` 或 `TODO-ARCH-yy`；
- 关闭所需的唯一证据；
- 未关闭时仍可执行的任务。

“阻塞”行必须逐项列出所有直接依赖该决定的任务，并可概括其后继；传递阻塞以任务卡“前置”和 DAG 推导。“未关闭时仍可执行”是 Gate 打开时的唯一派发白名单，禁止把“阻塞”列表的补集解释为可执行任务。

跨里程碑 ARCH Gate 使用相同字段，但只能通过明确引用现有里程碑 Gate、任务卡或验收状态施加限制。若对应能力尚未拆成任务卡，必须明记“当前无可派发任务”；Gate 关闭也不自动授权实现，必须先新增文件级白名单的原子任务卡。

`todoe-check.md` 中“候选策略已确认”和“Gate 可关闭”是两个不同状态：

- 文件头的批量确认记录可以一次冻结其中所有唯一勾选候选；冻结后执行模型不得改选，也不得继续按未选候选派发条件任务；
- 批量确认不补全外部事实、执行参数或验收证据，不自动关闭任何 Gate；
- 每个里程碑规格必须把已确认策略、活动条件分支、`not_applicable` 分支和剩余关闭证据写清楚。

一项人工 TODO 只有同时满足以下条件时，才可作为 Gate 的完整关闭证据：

1. 父级待办已勾选；
2. 候选项中恰好一个被勾选；
3. “决定”字段写明选项；
4. “决定人”和“日期”非空；
5. 若要求 ADR，ADR 已存在且状态为 accepted。
6. 该项所有 `需填写` 字段均已给出可复现值；涉及 Provider、工具或 live 路径时，runtime profile、授权夹具、无密钥命令、成功判定、证据路径、执行环境和负责人完整。

存在零个或多个候选被勾选，或任一关闭材料缺失时，执行模型必须保持 Gate open。候选策略已由批量记录确认但材料未齐时，可以继续执行 Gate 明确放行的 provider-neutral、Mock、契约或夹具任务。

## 6. 最小上下文包

派发器只向执行模型提供：

1. 根 `AGENTS.md`；
2. 本协议；
3. 对应执行规格的范围、公共不变量和相关 Gate；
4. 单一任务卡；
5. 已关闭 Gate 的证据；
6. 任务涉及的当前接口和 schema；
7. 任务开始时的 `git status --short`；
8. 已知文件占用和并发所有者。

不得一次传入整个仓库、全部任务卡、全部 Prompt 或未批准的候选实现。

## 7. 开始前检查

执行模型必须依次：

1. 读取最小上下文包；
2. 运行 `git status --short`；
3. 核对任务前置和 Gate；
4. 确认允许写入文件未被其他任务占用；
5. 记录输入文件和基线 revision/hash；
6. 先运行最窄的既有测试，确认基线状态。

若基线测试已经失败，先记录失败是否与任务相关；不得用本任务顺手修复无关失败。

## 8. 写入边界

- 只修改任务卡“允许写入”列出的文件。
- 通配目录只允许用于新包骨架、固定夹具目录或单一 Renderer feature；其他任务必须使用文件级白名单。
- 不改上位计划、ADR、其他任务 expected、冻结夹具或已接受 schema，除非任务卡显式授权。
- 不执行 `git add`、`git commit`、`git reset`、清理用户文件或全仓自动修复。
- 不新增依赖、Provider、模型、阈值、格式或自动应用策略；对应 Gate 未关闭时立即停止相关分支。
- 不用 Mock 结果证明 live Provider 路径通过。
- 不在验收任务中修改实现、测试预期、夹具、Prompt 或 schema。

## 9. 并发规则

- 一个可写文件同一时间只能属于一个任务。
- 共享 `src/index.ts`、`package.json`、锁文件、公共 schema 和路由文件的任务必须串行。
- 并行任务只能共享只读输入和冻结夹具。
- 后完成的任务不得覆盖先完成任务的接口；发现接口漂移时停止并重新审计前置。
- 派发器必须维护“任务 ID → 写文件”占用表；占用释放以验证结束和交接完成为准。

## 10. 验证层级

每张任务卡至少指定一个最窄验证命令。证据分为：

| 层级 | 证据 |
|---|---|
| L1 | 目标模块/纯函数测试 |
| L2 | 目标 package build、typecheck、test |
| L3 | 跨 package integration test |
| L4 | `pnpm run check` |
| L5 | 桌面交互、live Provider 或真实媒体样本 |

任务卡只声明实际完成的层级。L1～L4 不能替代 L5；L5 的环境或授权缺失时明确记为未验证。

任务结束前必须运行：

```bash
git diff --check
git status --short
```

## 11. 交接格式

```text
任务：Mx-YY
结果：complete | blocked | failed | not_applicable
修改文件：逐项列出
验证层级：L1～L5
验证：命令、退出码和关键结果
模型调用：none | mock | live-approved
输入基线：revision/hash
未验证：逐项列出
既有改动：是否保持不变
阻塞：TODO/Gate、错误文本或缺失输入
下一可执行任务：只列前置已满足的 ID
```

## 12. 里程碑完成审计

里程碑验收任务不得自行更新项目状态。负责人只能在独立变更中依据以下证据确认完成：

- 所有必需任务为 `complete`；
- 条件任务为 `complete` 或具有人工决策支持的 `not_applicable`；
- 全部 Gate closed；
- 冻结验收夹具 hash 未变化；
- package、integration 和全仓检查通过；
- live/交互要求有独立证据或被上位范围明确排除；
- 没有未解决的阻断项、未知数据丢失或未记录范围扩张。

文档完成、Mock 通过或未发现错误都不单独构成完成证据。
