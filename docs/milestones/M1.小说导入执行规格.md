## 3. 小模型执行与无人值守派发协议

### 3.1 任务状态与派发

每次只领取一个任务 ID，一个任务只交付一个可验证结果。任务只使用以下状态：

| 状态 | 含义 |
|---|---|
| `pending` | 前置未核对或尚未派发 |
| `ready` | 前置、文件占用和全部 Gate 均满足 |
| `in_progress` | 已由一个执行者领取 |
| `complete` | 单一结果和全部必测项均有证据 |
| `blocked` | 缺决策、依赖、环境或上游契约 |
| `failed` | 实现或验证失败且已记录证据 |
| `not_applicable` | 已关闭的条件分支明确排除该任务 |

禁止使用 `done`、`skip` 或 `mostly_complete` 等同义状态。文件头的“当前门禁”只摘要 G00，实际派发必须同时核对第 5 节全部 Gate、任务卡前置、DAG 和文件占用。Gate 打开时，“未关闭时仍可执行”是唯一派发白名单，不得把阻塞列表的补集视为可执行。

第 5 节是 M1 决策的唯一执行入口。“候选策略已确认”只冻结产品方向，不会自动补全参数、ADR 或验收证据，也不会自动关闭 Gate。执行模型不得重选候选项、代填缺失值或修改 Gate 状态。单一分支被阻塞时继续派发其他无依赖分支；白名单耗尽后输出阻塞清单、已完成证据和下一可执行任务。

### 3.2 最小上下文与开始检查

派发者只提供：根 `AGENTS.md`；本文件第 2～5 节；当前单一任务卡；已关闭 Gate 的证据；相关当前接口/schema；开始时的 `git status --short`；文件占用与并发所有者。不得一次附带 M1 全部源码或让执行模型规划下一任务。

开始前必须依次：

1. 读取最小上下文包；
2. 运行 `git status --short`，记录 staged、modified 和 untracked 文件；
3. 核对前置、Gate、DAG 和条件分支；
4. 确认“允许写入”文件未被其他任务占用；
5. 记录输入文件和 baseline revision/hash；
6. 先运行最窄的既有测试。基线已失败时记录关联性，不顺手修复无关失败。

### 3.3 写入、并发与停止边界

- 只修改任务卡“允许写入”列出的文件；一个可写文件同时只属于一个任务。
- 共享 `src/index.ts`、`package.json`、锁文件、公共 schema 或路由的任务串行；并行任务只共享只读输入和冻结夹具。
- 目录通配只能用于任务卡明确授权的新包骨架、固定夹具或单一 Renderer feature；文件占用只在验证和交接完成后释放。
- 后完成的任务不得覆盖先完成任务的接口；发现接口漂移时立即停止，重新审计前置、基线 revision/hash 和文件占用。
- 公共类型从 `src/index.ts` 导出，文件名使用 camelCase，包目录使用 kebab-case。
- 测试放在目标包 `test/*.test.mjs`，从构建后的 `dist` 导入；先写失败夹具或测试，再写最小实现。
- 不修改上位计划、阶段文档、ADR、冻结 schema/fixture/expected 或 `docs/ideas/`，除非任务卡显式授权。
- 不新增未批准依赖、Provider、模型、阈值、格式或自动应用策略；需要时立即以 `blocked` 停止。
- 不执行 `git add`、`git commit`、`git reset`、用户文件清理或全仓自动修复；不覆盖既有改动。
- 验收卡不得修改实现、测试预期、夹具或 schema；Mock 不得证明 live 路径通过。

### 3.4 验证与交接

证据分层：L1 目标模块/纯函数测试；L2 目标 package build/typecheck/test；L3 跨 package integration test；L4 `pnpm run check`；L5 桌面交互、live Provider 或真实样本。L1～L4 不替代 L5，环境或授权缺失时必须记为未验证。任务结束前运行：

```bash
git diff --check
git status --short
```

交接必须使用：

```text
任务：M1-XX
结果：complete | blocked | failed | not_applicable
修改文件：逐项列出
验证层级：L1～L5
验证：命令、退出码和关键结果
模型调用：none | mock | live-approved
输入基线：revision/hash
未验证：逐项列出
既有改动：是否保持不变
阻塞：Gate、错误文本或缺失输入
下一可执行任务：只列前置已满足的 ID
```

只有单一结果和全部必测项都有证据才能标记任务 `complete`。只有所有必需任务 complete、条件任务 complete/not_applicable、全部 Gate closed、冻结夹具 hash 未变、L1～L4 通过且必需 L5 有独立证据时，负责人才能在独立变更中确认里程碑完成。

## 4. 公共不变量

所有任务共同遵守：

- 原始文件和已登记 `SourceAsset` 不可原地修改；
- 正式产物只能在完整校验后通过阶段 00 workflow 提交；
- 适配器只做格式探测、验证和提取，不做校对、角色推断或音频处理；
- `rawText`、`canonicalText` 和 `normalizedText` 不得共用可变文件；
- 文本范围统一使用半开区间 `[start, end)`，并在契约中显式声明 offset 单位；
- offset、行号、标题和显示顺序是定位属性，不是稳定实体 ID；
- 规则无法确定时产生 issue/review，不得猜测后写入正式索引；
- 任意删除或替换都必须有结构化 diff；
- Chapter 和块范围必须单调、不重叠；未覆盖范围不得静默丢弃；
- 相同输入、处理器版本和参数必须得到相同输入指纹；
- 失败重试不得覆盖已提交 revision，也不得自动删除旧产物。

统一错误码至少包括：

```text
NOVEL_IMPORT_UNSUPPORTED_FORMAT
NOVEL_IMPORT_INVALID_SOURCE
NOVEL_IMPORT_ENCODING_REQUIRED
NOVEL_IMPORT_STRUCTURE_INVALID
NOVEL_IMPORT_REVIEW_REQUIRED
NOVEL_IMPORT_STALE_SESSION
NOVEL_IMPORT_DEPENDENCY_UNAVAILABLE
NOVEL_IMPORT_RESOURCE_LIMIT_EXCEEDED
NOVEL_IMPORT_BUDGET_INVALID
```

新增错误码必须先进入契约测试，禁止在各适配器中创建同义错误码。

### M1-D02：TXT 编码策略

状态：`closed`。

本地决策项 M1-C02 的候选：A）BOM/严格 UTF-8 自动确认，其他编码必须人工选择（已选）；B）检测器达到版本化阈值后自动确认；C）MVP 只支持 UTF-8。

已确认策略（2026-08-08）：方案 A。BOM 或严格 UTF-8 可自动确认，其他编码必须由用户显式选择。

关闭结论（2026-08-09）：

- 持久化编码 ID 只允许 `utf-8`、`gbk`、`gb18030`、`big5`、`utf-16le`、`utf-16be`。UI 可把 `gbk` 显示为“GBK / GB2312”，但契约、revision 和指纹不得保存 `gb2312`、`gb_2312` 等别名；WHATWG 标签表把这些别名映射到 GBK，而 `gb18030` 是独立编码：<https://encoding.spec.whatwg.org/>。
- BOM 必须先按最长签名判定：`00 00 FE FF` 和 `FF FE 00 00` 是本合同不支持的 UTF-32，返回 `NOVEL_IMPORT_INVALID_SOURCE`/`unsupported_utf32_bom`；随后才允许 `EF BB BF` → `utf-8`、`FF FE` → `utf-16le`、`FE FF` → `utf-16be`。无 BOM 时，只有整个输入通过严格 UTF-8 解码才能自动记为 `utf-8`，纯 ASCII 作为 UTF-8 子集按同一规则接受。BOM 与显式人工选择冲突时返回 `NOVEL_IMPORT_INVALID_SOURCE`，detail reason 为 `encoding_bom_conflict`，不得静默覆盖。UTF BOM 签名依据 <https://www.unicode.org/faq/utf_bom.html#bom>。
- 无 BOM 且严格 UTF-8 失败、调用方又未提供人工选择时返回 `NOVEL_IMPORT_ENCODING_REQUIRED`。人工选择仅允许上述非 UTF-8 ID；未知 ID 在进入解码前拒绝。每次人工确认必须绑定 `sourceContentHash` 与所选 canonical encoding ID，源 hash 改变后不得沿用确认。
- 解码统一使用 Node.js `TextDecoder(label, { fatal: true, ignoreBOM: true })` 并以 `decode(chunk, { stream: true })` 流式处理；最终必须无 `stream` 调用一次完成 flush。`ignoreBOM: true` 用于把已识别 BOM 作为 leading `U+FEFF` 保留在 `extracted/raw`，由 canonical 任务删除并记录变换，而不是在解码边界静默丢弃。Node.js 的 `fatal`、`ignoreBOM` 和流式行为见 <https://nodejs.org/download/release/v24.18.1/docs/api/util.html#class-utiltextdecoder>。
- 任一 decoder error 返回 `NOVEL_IMPORT_INVALID_SOURCE`，detail reason 为 `encoding_decode_failed`，并记录 canonical encoding ID 与包含失败位置的源字节 chunk 半开范围；不得插入 decoder 产生的 `U+FFFD`。源文本本来就合法包含 `U+FFFD` 时保留原值并产生 `source_contains_replacement_character` review warning，不自动改写。
- 混合编码不做启发式猜测：若严格解码失败则按上项阻断；若用户明确选择的 decoder 可完整解码，则保存该人工确认和预览证据。后续发现乱码必须重新选择并产生新 run，不覆盖旧 revision。
- 不引入编码检测依赖、置信阈值或系统默认编码。Core 启动时必须探测上述 decoder；缺失 legacy decoder 时返回 `NOVEL_IMPORT_DEPENDENCY_UNAVAILABLE`，不得降级到替换解码。

关闭证据：决策负责人为 M1 主任务负责人；目标开发环境固定为根 `engines` 和 `.nvmrc` 对应的 Node `24.18.1`。2026-08-09 执行 built-in probe，确认 `process.config.variables.icu_small === false`、ICU `78.3`、六个 canonical ID 均可实例化、GBK/GB18030/Big5 中文样例可解码、非法 UTF-8 在 `fatal: true` 下抛出 `TypeError`。实现验收仍必须把 BOM、无 BOM 严格 UTF-8、每个人工 ID、chunk 边界截断、多编码冲突、非法尾字节和 packaged Core capability probe 加入 M1-04/M1-17 测试；这些是已关闭合同的下游验证，不再是待选决策。

### M1-D03：稳定 ID 与 offset 契约

状态：`closed`。

本地候选基线：

- M1-C03：A）文本范围使用 UTF-16 code unit，SourceLocator 另存 byte/line/EPUB locator 且字段显式带 `offsetUnit`；B）文本范围使用 Unicode code point；C）全部文本范围使用 UTF-8 byte（已选）。
- M1-C04：A）持久化 opaque ID，重导入按 locator、内容 hash 与邻接锚点对齐，歧义进入 review（已选）；B）ID 由内容 hash 派生；C）ID 由 offset/order 派生。

已确认策略（2026-08-08）：

- M1-C03 方案 C：所有文本范围使用 UTF-8 byte，并继续使用半开区间；
- M1-C04 方案 A：首次生成持久化 opaque ID，重导入使用 locator、内容 hash 和邻接锚点重对齐，歧义进入 review。

关闭结论（2026-08-09）：

1. `TextRangeV1` 固定字段为 `textRevisionId`、`textLayer`（`raw | canonical | normalized`）、`offsetUnit: "utf8-byte"`、`startByte`、`endByte`。每个文本 revision 必须同时记录 exact UTF-8 artifact 的 `contentHash` 与 `byteLength`；范围只相对于该不可变 revision 的 UTF-8 字节数组，不得相对于 JavaScript UTF-16 code unit、Unicode code point、当前活动 revision 或拼接后的 UI 字符串。
2. 范围统一为半开区间。校验必须证明两端为安全整数、`0 <= startByte <= endByte <= byteLength`、revision/layer 匹配，并且两端均落在 UTF-8 scalar 边界；实现按 artifact bytes 切片，不得直接用数值对 JavaScript string 调用 `slice`。UTF-8 长度使用 `Buffer.byteLength(text, "utf8")` 或 exact encoded buffer 长度，依据 <https://nodejs.org/download/release/v24.18.1/docs/api/buffer.html#static-method-bufferbytelengthstring-encoding>。
3. `TxtSourceLocatorV1` 固定包含 `sourceAssetId`、`sourceContentHash`、`sourceEncoding`、`sourceByteRange: { offsetUnit: "source-byte", startByte, endByte }`、`rawTextRange: TextRangeV1`、`lineRange: { lineBase: 1, startLine, endLineExclusive }`。`sourceByteRange` 相对于不可变原始文件字节，允许与转码后的 UTF-8 长度不同，不得冒充 `TextRangeV1`；CRLF 视为一个换行，CR/LF 各自视为一个换行，行范围同样半开。BOM 的原始字节必须可定位，leading `U+FEFF` 在 raw → canonical 删除时留下映射记录。TXT source-backed block 的 `sourceByteRange` 必须非空；同一 ImportedNovel 内不得有两个 block 共享下述 exact-locator 投影。
4. exact-locator 比较投影唯一固定为 `[sourceEncoding, sourceByteRange.startByte, sourceByteRange.endByte]`，`offsetUnit` 因恒为 `source-byte` 不重复进入 key。`sourceAssetId` 只用于把 locator 反查到本次不可变 SourceAsset，跨 run 即使不同也不得影响相等判断；`sourceContentHash` 用于校验 locator 所属字节快照，并决定进入“相同 source hash”还是“变化 source hash”优先级，不进入位置投影；`rawTextRange` 绑定本次 raw revision，`lineRange` 是显示/诊断派生值，二者均不得参与 exact 比较。只有 old/new canonical encoding ID 与 source byte 半开范围全部相等才是 exact locator；投影不唯一或 locator 与各自 SourceAsset hash/size 不一致时必须先返回结构错误，不得进入 ID 对齐。
5. raw → canonical、canonical → normalized 的每次变换必须保存版本化、单调的 range map。每段固定包含连续的 `segmentIndex`、`identity | replace | delete | insert`、输入 revision/range、输出 revision/range、rule ID/version 和前后 SHA-256，输入/输出 range 永远存在：`insert` 使用输入零长锚点 `[p,p)` 和非空输出范围，`delete` 使用非空输入范围和输出零长锚点 `[q,q)`，`identity/replace` 两侧均非空，零长到零长非法；`identity` 还要求两侧 byte length 与 exact bytes 相同。按 `segmentIndex` 遍历时，输入 `startByte/endByte` 与输出 `startByte/endByte` 都必须各自非递减；忽略零长锚点后，输入非空段必须无重叠、无缺口覆盖整个输入 revision，输出非空段同样完整覆盖输出 revision。同一输入锚点的连续 `insert` 构成一个最大 insert anchor group，其输出范围必须按 `segmentIndex` 首尾相接；同一输出锚点的连续 `delete` 同理构成最大 delete anchor group，其输入范围必须首尾相接。group 内外都只按 `segmentIndex` 排序，不得由对象键、rule 名或运行时遍历顺序重排；相同锚点但不连续的 segment 是非法 map。
6. 零长 anchor group 位于左侧半开范围之后、右侧半开范围之前，不归属任一相邻非空范围。对 insert group 的 source cursor `p`，显式 `before` 映射到该 group 第一段输出范围的起点，`after` 映射到最后一段输出范围的终点；对 delete group 的 target cursor `q`，`before` 映射到该 group 第一段输入范围的起点，`after` 映射到最后一段输入范围的终点。非空 `TextRangeV1` 映射固定使用 start=`after`、end=`before`，所以端点处 insert/delete 不被偷偷并入；零长 `TextRangeV1` 按 cursor 处理，调用方必须为该 cursor 显式传一个 `before | after` bias 并将结果作为同一点的 start/end，不存在默认 bias。
7. range map 遍历返回有序 `mappedFragments` 与 `unmappableFragments`，不得先求外包围范围：`identity` 可按 byte delta 映射任意合法子范围；`replace` 只有请求覆盖整个 segment 时才能整体映射，部分相交必须记为 `range_unmappable`；source → target 遇到 `delete`、target → source 遇到 `insert` 时必须返回带对应零长锚点的 unmappable fragment。跨多个 revision 时逐 map、逐 fragment 保序传递；只有同一目标 revision/layer、连续且均来自相邻 `identity` segment，并且中间没有 replace/insert/delete/unmappable，才允许合并。要求单一范围的调用只有在一个 fragment 完整覆盖请求且无 unmappable 时成功，否则返回 `NOVEL_IMPORT_REVIEW_REQUIRED`/`range_unmappable`，不得跨缺口合并或用最近边界猜测。任何跨层反查必须使用已保存 map，不得重新运行当前规则推算旧 revision offset。
8. `blockId`、`chapterCandidateId` 和 `chapterId` 首次持久化统一使用 Node.js `crypto.randomUUID()` 生成 UUID v4；ID 是 opaque value，不编码 hash、offset、order、title 或 source path。Node API 见 <https://nodejs.org/download/release/v24.18.1/docs/api/crypto.html#cryptorandomuuidoptions>，UUID v4 位布局见 <https://www.rfc-editor.org/rfc/rfc9562.html#name-uuid-version-4>。
9. block 重对齐只考虑尚未复用、`kind` 相同且 exact UTF-8 block `contentHash` 相同的旧 block。优先级固定为：`sourceContentHash` 相同且 exact-locator 投影相等；`sourceContentHash` 不同但 exact-locator 投影相等；两侧最近非空 block hash 锚点；单侧锚点加已匹配 block 的单调顺序；最后才是全书唯一且顺序不冲突的 content hash。每一级只有恰好一个候选才能复用旧 ID；候选为零时生成新 ID，候选多于一个或最高等级平分时生成新 ID 并产生 `ambiguous_reimport_alignment` review，不得用距离、标题、行号或数组顺序破平。
10. Chapter 仅在旧 heading block ID 可唯一复用，或首尾已复用内容 block anchor 可唯一确定同一边界时复用 `chapterId`；显示序号、标题格式和 order 变化本身不创建新 ID。边界 anchor 平分、重复标题/正文或覆盖范围无法唯一证明时生成新 ID 并进入 review。
11. hash 固定为 exact bytes 的 SHA-256 lowercase hex；不得在 hash 前执行未记录的 Unicode normalization。组合字符、预组合字符和兼容字符是否转换只能由版本化 canonical rule 决定并产生 range map；Unicode normalization 风险依据 <https://www.unicode.org/reports/tr15/>。

关闭证据：决策负责人为 M1 主任务负责人；合同版本为 `TextRangeV1`、`TxtSourceLocatorV1`、range map `m1-text-range-map-v1` 和 alignment policy `m1-block-alignment-v1`。2026-08-09 在 Node `24.18.1` probe 中，样例 `A中😀é` 的 JavaScript string length 为 `6`、UTF-8 byte length 为 `11`，证明实现验收不能复用 UTF-16 index；同一 probe 的 `randomUUID()` 通过 UUID v4 pattern。M1-02/M1-06 必测中文三字节、emoji 四字节、组合字符、CRLF、首部插入、局部修改、重复内容、跨 SourceAsset ID 的同 hash exact locator、变化 hash 的同位置、locator 投影重复/越界、双侧/单侧 anchor、平分歧义、非法 byte boundary，以及 identity/replace/insert/delete 的零长锚点、before/after、部分 replace、跨 map unmappable 和禁止跨 gap 合并；这些是已关闭合同的实现证据。
