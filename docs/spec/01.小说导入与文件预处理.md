# 阶段 01：小说导入与文件预处理

状态：`planned`
实现审计：`unverified`
前置阶段：[00 项目基线与工程工作区](./00.项目基线与工程工作区.md)

## 1. 目标

把不同来源、格式和质量的小说文件转换为统一、可追踪、可校验的结构化小说数据，为校对、剧本、角色、发音和 TTS 提供稳定输入。

核心原则：程序执行确定性提取、切分和持久化；LLM 只处理规则无法可靠判断的语义分类和边界候选，不得输出或改写整本小说。

## 2. 范围

第一阶段完成范围：

- TXT、EPUB、Markdown 输入；
- 格式识别、验证和统一提取；
- `extracted/raw`、`canonical`、`normalized` 三层；
- 行、块和来源定位；
- 卷、章节候选、章节索引、切分和完整性报告；
- Scene 语义边界；
- `ProcessingSegment` 技术分块；
- 规则优先、LLM 回退、Prompt 版本和调用缓存；
- 包内测试/诊断入口、检查能力、审计、恢复和测试夹具；该入口不构成架构第 15 节的外部 CLI adapter。

MVP M1 只要求 TXT 完整导入。EPUB 与 Markdown 属于阶段 01 的后续完成条件，不阻塞 M1 和最小 TXT 纵向切片；重新纳入某个里程碑前必须先补依赖、资源预算和验收任务。Scene 与 `ProcessingSegment` 的领域要求仍定义在本阶段，但已确认由 M2-01A、M2-01B 作为“阶段 01 桥接”实现和验收；它们不是 M2 的上游输入。

## 3. 非目标

- 不处理错别字、人名误用、多音字和文学语义校正；
- 不生成角色、最终说话人、情绪、发音或音频；
- `ProcessingSegment` 不等于后续 `ScriptUnit`；
- 不自动补写缺失章节；
- 不在本阶段支持 DRM 绕过；
- DOCX、HTML、PDF/OCR、MOBI/AZW 和压缩包延后。

## 4. 格式适配器

后续处理不得感知 TXT、EPUB 或 Markdown 的私有实现：

```ts
interface NovelSourceAdapter {
  readonly adapterId: string;
  readonly adapterVersion: string;

  probe(source: SourceAsset): Promise<ProbeResult>;
  validate(source: SourceAsset): Promise<ValidationResult>;
  extract(source: SourceAsset, context: ImportContext): Promise<ImportedNovel>;
}
```

- `probe` 综合文件签名、容器结构、媒体类型和扩展名，不只看扩展名；
- `validate` 在正式产物创建前返回阻断错误和警告；
- 适配器提取元数据、阅读顺序、块结构和 `source_locator`；
- 适配器不得执行校对、角色推断或音频处理；
- 第一版采用显式内置注册表，不要求运行时第三方插件；
- 多个适配器同时命中时记录置信度和选择原因，无法可靠判断时要求人工选择。

端口与适配器边界参考：

https://alistair.cockburn.us/hexagonal-architecture

EPUB 必须遵循容器、package、manifest、spine、navigation 和 content document，不得按 ZIP 文件名排序正文。W3C EPUB 3.3：

https://www.w3.org/TR/epub-33/

## 5. 统一导入模型

```ts
interface ImportedNovel {
  sourceAssetId: string;
  sourceHash: string;
  adapterId: string;
  adapterVersion: string;
  metadata: NovelMetadata;
  orderedBlocks: DocumentBlock[];
  structuralHints: StructuralHint[];
  warnings: ImportWarning[];
}

interface DocumentBlock {
  blockId: string;
  kind: "heading" | "paragraph" | "quote" | "list" | "separator" | "unknown";
  rawText: string;
  sourceLocator: SourceLocator;
  contentHash: string;
}
```

`block_id` 必须在内容不变时尽可能稳定，不能只使用全文字符偏移。行号和偏移是定位属性，不是实体身份。

## 6. 文本层

### 6.1 extracted/raw

从源格式提取的文本和结构，不修改语义；必须保留源文件、容器条目、元素或字节范围等可用定位。

### 6.2 canonical

仅执行确定性基础标准化：

- 编码统一为 UTF-8；
- BOM 和非法控制字符处理；
- CRLF、CR、LF 统一为 `\n`；
- 明确规则下的 Unicode、全角数字/英文和空白标准化；
- HTML/XML 解析为结构块；
- 保留中文标点、破折号、省略号、书名号、引号和段落语义。

编码无法可靠识别时必须进入人工复核，不得猜测后覆盖源文件。

### 6.3 normalized

只处理排版和噪声：广告、水印、重复页眉页脚、重复标题、异常空行和残留标签。所有删除必须记录范围、前后内容、理由、来源、置信度和操作者。

噪声处理流程：

```text
候选发现 → 规则判断 → 必要时 LLM 判断 → 人工/策略确认 → 程序应用 diff
```

不得使用巨型关键词表直接批量删除，所有高风险批量操作必须支持 dry run。

## 7. 章节识别

```text
文档结构 + 规则候选 + 目录证据 + 全书模式
                      ↓
              不确定候选的 LLM 判断
                      ↓
                  ChapterIndex
                      ↓
             程序按范围确定性切分
```

至少识别：章、回、节、卷、序章、楔子、前言、引子、终章、尾声、番外、后记以及常见英文 Chapter 形式。

章节候选至少记录：

```ts
interface ChapterCandidate {
  id: string;
  line: number;
  startOffset: number;
  endOffset: number;
  rawTitle: string;
  normalizedTitle: string;
  rule?: string;
  ruleConfidence: number;
  contextBefore: string[];
  contextAfter: string[];
}
```

必须实现统一序号解析，支持阿拉伯数字、常见中文数字和卷内章节重新编号。章节 ID 与标题、显示编号和顺序分离；插入或重排章节不得要求整体重建稳定 ID。

## 8. ChapterIndex 和校验

ChapterIndex 至少记录：

```text
chapter_id
order
volume_id / volume_number
chapter_number
title / raw_heading
heading_start
content_start / content_end
source_line_range
confidence
detected_by
```

正式切分前必须校验：

- offset 合法、单调且不重叠；
- 所有输入范围均被分类为 front matter、chapter、appendix、noise 或 unknown；
- 覆盖率及未覆盖范围可查看；
- 正文和目录冲突时保留正文顺序并报告冲突；
- 重复编号、标题、正文、缺号、乱序、超短和超长章节只产生问题记录，不自动删除或补写；
- 近似重复只作为 `probable_duplicate_content`，必须人工确认。

规则无法判断时，LLM 只接收候选及有限上下文，并返回通过 JSON Schema 校验的分类、边界、证据和置信度。失败重试达到上限后进入复核，不得写入正式索引。

## 9. Scene 和 ProcessingSegment

Scene 是连续叙事场景，可由时间、地点、叙事视角、主要人物集合、事件、梦境/回忆和明确分隔符变化形成候选。规则无法判断时只向 LLM 提供边界前后段落。

Scene 不按固定字数或每句对白切分。角色信息在本阶段仅为候选 metadata，最终身份由阶段 04 解析。

`ProcessingSegment` 解决模型上下文、并发、缓存和失败恢复：

```ts
interface ProcessingSegment {
  segmentId: string;
  chapterId: string;
  sceneId: string;
  order: number;
  text: string;
  sourceRange: TextRange;
  contextBefore?: string;
  contextAfter?: string;
  contentHash: string;
}
```

正式 Segment 不复制 overlap；模型上下文通过独立字段传入。切分优先使用段落、完整对话和句末标点，最大长度由处理器能力配置。

## 11. 页面和检查能力

项目内至少提供：

- 导入小说并显示格式、大小、哈希和适配器选择；
- 查看 raw、canonical、normalized 差异；
- 查看章节候选、目录证据、覆盖率和异常；
- 人工调整章节边界、分类未覆盖文本；
- dry run 查看拟删除噪声；
- 查看 Scene 和 ProcessingSegment；
- 只重新执行选择的任务或范围。

包内测试/诊断入口至少支持导入、标准化、章节检测、章节校验、Scene/Segment 生成和 inspect；不得暴露 Application Core 入站 CLI transport 或作为产品命令安装。

## 12. 版本和过期影响

- 新源文件产生新的 `SourceAsset` revision；
- adapter、规则或 Prompt 版本改变只有在新结果被激活后才传播过期；
- 内容未变化且块可稳定对齐时，保留其下游依赖；
- 修改章节边界只影响相交章、Scene、Segment 及下游；
- 仅修改标题显示信息时，不应使片段音频过期，除非朗读或导出显式依赖标题；
- 删除确认必须创建新的 normalized revision，旧内容保留。

## 13. 早期实现迁移

取得旧解析代码后重点检查：

- 是否把所有格式写进同一个条件分支；
- 是否只按扩展名识别；
- 是否覆盖原文；
- 是否混合标准化、噪声删除和语义纠错；
- 是否使用易漂移 offset 或章节顺序作为唯一 ID；
- 是否把章节 TXT 文件当作唯一真值；
- 是否通过单一线性状态判断全部完成；
- 是否能生成 diff、覆盖率和来源定位。

违反原文不可变或无法定位来源的实现标记为 `replace`；纯规则、解析器和验证器可按契约决定 `retain` 或 `adapt`。

## 14. 测试要求

### 14.1 适配器契约

- 不修改源资产；
- 相同输入和版本产生稳定结构；
- 块顺序和来源定位完整；
- 破损输入不产生正式半成品；
- 元数据缺失、空内容、非法编码和损坏容器有明确错误。

### 14.2 Golden Test

使用可再分发夹具覆盖标准中文、噪声网文、繁体、英文、Markdown 和 EPUB；保存人工确认的章节索引并比较 precision、recall 和 boundary accuracy。阈值由基准 ADR 确定，不在本文预设。

### 14.3 属性不变量

- Chapter、Scene、ProcessingSegment 范围单调且不重叠；
- ID 唯一；
- 未确认清洗前，拼接结构单元可还原 canonical 文本；
- normalized 与 canonical 的差异全部有 diff；
- Segment 拼接不丢字、不重复正文；
- 失败重试不会覆盖已提交 revision。

## 15. 交付切片

### P0

TXT、常见中文编码、canonical、规则章节索引、确定性切分、编号/顺序/覆盖率校验、包内测试/诊断入口、单元测试。

### P1

EPUB、Markdown、LLM 章节回退、重复正文、长度异常、噪声候选、Prompt 版本和缓存。

### P2

Scene、ProcessingSegment、人工复核、完整 audit、dry run 和页面检查能力。

### P3（未纳入当前计划）

DOCX、HTML、PDF/OCR、MOBI/AZW 和批量压缩包未纳入当前计划；未来启用前必须重新批准并更新主计划与原子任务。

## 16. 验收标准

- TXT 在 M1 可以完整导入；EPUB 与 Markdown 在阶段 01 完成前另行交付；
- 原始文件和 raw 永不覆盖；
- 章节索引通过范围、顺序和覆盖率校验；
- 所有未覆盖文本有分类或待审状态；
- 规则优先，LLM 只处理不确定候选并返回结构化结果；
- Chapter、Scene、ProcessingSegment 可反查源位置；
- 所有删除有 diff 和审核记录；
- 任一任务失败可按最小范围重试；
- 重新导入或调整边界只使实际依赖的下游过期。
