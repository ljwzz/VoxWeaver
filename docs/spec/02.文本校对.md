# 阶段 02：文本校对

状态：`planned`
实现审计：`unverified`
前置阶段：[01 小说导入与文件预处理](./01.小说导入与文件预处理.md)

## 1. 目标

在不覆盖源文件、raw、canonical 或 normalized 的前提下，产生可追踪、可撤销、可人工复核的 `corrected` 文本。

## 2. 范围

- 错别字、OCR 错误、标点、重复文字和明显文本异常；
- 人名、地名、称谓和项目术语的一致性候选；
- 修改分级、置信度、证据、审核和批量应用；
- normalized 与 corrected 的稳定块映射；
- 修改后最小范围的下游过期传播。

## 3. 非目标

- 不进行文学润色、风格改写或剧情补写；
- 不自动补全缺失章节；
- 不处理最终发音表达和数字朗读；
- 不直接确认角色身份或说话人；
- 不修改 `normalized` revision。

## 4. 修改等级

```text
SAFE       高确定性且不改变语义，可按项目策略批量应用
REVIEW     依赖语境或知识库，必须人工确认或抽检
DANGEROUS  可能改变原意，默认禁止自动应用
```

等级只决定处理策略，不代替置信度和证据。阈值必须通过样章基准校准，不能把示例数值当成生产标准。

## 5. 数据契约

```ts
interface CorrectionProposal {
  proposalId: string;
  chapterId: string;
  blockId: string;
  sourceRange: TextRange;
  category: "typo" | "ocr" | "punctuation" | "duplicate" | "entity" | "grammar" | "other";
  level: "safe" | "review" | "dangerous";
  before: string;
  after: string;
  reason: string;
  evidence: string[];
  confidence: number;
  producer: "rule" | "llm" | "manual";
  processorVersion: string;
  dictionaryVersion?: string;
  reviewStatus: "pending" | "accepted" | "rejected";
}
```

每次应用产生新的 corrected revision，并保存：

- 基线 normalized revision；
- 被接受和拒绝的 proposal；
- 应用顺序与冲突解决；
- 前后内容哈希；
- 操作者和时间；
- 未解决候选。

跨进程结果使用 JSON Schema Draft 2020-12：

https://json-schema.org/specification

## 6. 处理流程

```text
规则与词典扫描
  ↓
候选合并和冲突检测
  ↓
必要时 LLM 语境判断
  ↓
结构化 proposal 校验
  ↓
SAFE 策略 / REVIEW 队列 / DANGEROUS 阻断
  ↓
人工确认
  ↓
程序应用 diff 并生成 corrected revision
```

LLM 只输出修改候选、理由、证据和置信度；不得返回重写后的整章作为正式结果。所有修改由程序按稳定范围应用。

## 7. 知识库关系

校对阶段可以读取当前项目的：

- 人物名和别名候选；
- 地名、组织、物品和世界观实体；
- 禁改词；
- 人工锁定写法；
- 已确认的跨章一致性规则。

角色注册表尚未完成时，实体结果只能作为候选。后续角色归并可以触发新的校对候选，但不得静默重写已审核文本。

## 8. 页面和人工审核

页面必须支持：

- 原文、normalized、proposal 和 corrected 并排对照；
- 按等级、类别、章节、实体和置信度筛选；
- 单条接受、拒绝、编辑和批量处理 SAFE；
- 查看建议依据、处理器和词典版本；
- 撤销当前草稿，或基于历史 revision 新建草稿；
- 提交前预览受影响的剧本、发音和音频范围。

人工编辑必须转化为显式 proposal 或 edit record，不得绕过审计直接修改文件。

## 9. 版本和过期影响

- 修改一个块，只使与该块相交的 Scene、剧本、spoken、音频和下游消费者过期；
- 只改变 proposal 备注或拒绝理由，不使内容消费者过期；
- 人物写法变化可以触发实体和角色候选重分析，但不得使无命中章节过期；
- 修改恢复为已有内容时，允许按输入指纹复用历史下游产物；
- 旧 corrected revision 和审核记录必须保留。

## 10. 早期实现迁移

重点检查旧实现是否：

- 直接覆盖 normalized 或原文；
- 把 LLM 整章输出当作正式文本；
- 无法记录单条 diff；
- 使用固定置信度阈值却没有基准；
- 只保存接受结果而丢失拒绝理由；
- 文本变更后把整本书全部标记重做。

覆盖原文或无法回溯单条修改的实现标记为 `replace`。可复用的规则、词典和差异算法按契约标记 `adapt`。

## 11. 测试要求

- 相同输入、规则和模型版本产生稳定 proposal；
- proposal 范围不重叠或有确定冲突策略；
- SAFE/REVIEW/DANGEROUS 路由正确；
- 批量应用后所有差异可逆；
- 专有名词不会被通用纠错器静默修改；
- LLM 非法 JSON、越界修改和整章改写被拒绝；
- 修改一个块只传播到相交下游；
- 多人并发或基线变化时拒绝盲写。

## 12. 验收标准

- 原始层和 normalized 层不可变；
- 每一处 corrected 差异都能回答改了什么、为何修改、谁确认、使用什么版本；
- 危险修改不能自动进入活动版本；
- 所有 AI 修改可撤销和复现；
- 项目术语和实体写法可以跨章节复用；
- 下游影响按块和 ScriptUnit 最小化。
