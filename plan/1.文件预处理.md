# 小说文件预处理模块：工程实现提示词

你需要为一个“AI 有声小说生产系统”实现第一阶段：**小说文件预处理 Pipeline**。

该模块负责把不同来源、不同格式、质量不一的小说文件，转换为统一、可追踪、可校验的结构化小说数据，为后续：

* 文本纠错
* 多音字处理
* 剧本转换
* 角色识别
* Scene 切分
* 情绪分析
* TTS
* 音频后期

提供稳定的数据基础。

本阶段的核心原则：

> **程序负责确定性处理，LLM 负责语义判断。**
>
> 不允许让 LLM 直接输出“处理后的整本小说”或“重新生成章节内容”。
>
> LLM 应尽量只输出：
>
> * 分类结果
> * 章节索引
> * 边界位置
> * 删除建议
> * 异常判断
> * Scene 边界
> * 置信度
>
> 最终文本切割、删除、合并、保存等操作必须由程序工具执行。

---

# 1. 模块目标

实现完整流水线：

```text
Source File
    ↓
格式识别
    ↓
文本提取
    ↓
基础标准化
    ↓
结构/行信息构建
    ↓
章节标题候选发现
    ↓
规则章节识别
    ↓
LLM 辅助章节识别
    ↓
Chapter Index
    ↓
章节索引校验
    ↓
程序确定性切分
    ↓
章节文本清洗
    ↓
章节完整性分析
    ↓
重复 / 缺失 / 顺序异常检测
    ↓
Scene 切分
    ↓
Segment 切分
    ↓
结构化小说数据
```

必须确保：

```text
原始文件永远不可覆盖。
所有处理步骤可追踪。
所有文本修改可审计。
所有步骤可以单独重新执行。
处理中断后可以恢复。
LLM 输出错误不能直接破坏原始文本。
```

---

# 2. 第一版输入格式

优先支持：

```text
TXT
EPUB
Markdown
```

后续预留：

```text
DOCX
PDF
HTML
MOBI
AZW
ZIP / 7z 批量导入
```

设计统一接口：

```ts
interface DocumentExtractor {
  supports(file: SourceFile): boolean;

  extract(file: SourceFile): Promise<ExtractedDocument>;
}
```

输出统一为：

```ts
interface ExtractedDocument {
  sourceType: "txt" | "epub" | "markdown";

  metadata: {
    title?: string;
    author?: string;
    language?: string;
  };

  blocks: DocumentBlock[];
}
```

不要让后续章节识别模块感知 EPUB/TXT/Markdown 的具体实现。

---

# 3. 原始数据必须保留

至少保留三种文本。

```text
rawText
canonicalText
normalizedText
```

定义：

### rawText

从源文件提取出的原始文本。

原则：

```text
只读取
永远不修改
```

用于：

* 问题追踪
* 人工检查
* 重新处理
* 数据恢复

---

### canonicalText

仅执行不会改变小说语义的基础标准化。

例如：

```text
编码统一
换行统一
BOM 删除
非法控制字符处理
HTML/XML 标签解析
EPUB 页面结构转换
```

章节识别主要基于：

```text
canonicalText
```

---

### normalizedText

章节切分之后进一步清洗得到。

可能包括：

```text
广告删除
网站水印删除
重复标题删除
多余空行处理
明显排版问题修复
```

后续 NLP / LLM / TTS 使用：

```text
normalizedText
```

不要在生成章节索引之前进行大规模语义文本修改。

---

# 4. 文本标准化

实现：

```ts
normalizeDocument()
```

但标准化必须拆成多个可追踪步骤，而不是一个巨大的 replace。

例如：

```text
normalizeEncoding
normalizeBom
normalizeLineEnding
normalizeUnicode
normalizeWhitespace
removeControlCharacters
normalizeHtml
normalizeParagraph
detectNoise
removeConfirmedNoise
```

每一个步骤产生：

```ts
interface TransformRecord {
  type: string;
  beforeHash: string;
  afterHash: string;

  changes: TextChange[];

  createdAt: string;
}
```

---

# 5. 编码处理

TXT 文件需要处理：

```text
UTF-8
UTF-8 BOM
GBK
GB18030
Big5
UTF-16
```

最终统一：

```text
UTF-8
```

如果编码无法可靠判断：

```text
标记 requiresReview
```

不要直接猜测后保存。

---

# 6. 换行标准化

统一：

```text
CRLF
CR
LF
```

为：

```text
\n
```

同时建立：

```text
lineNumber
charStart
charEnd
```

例如：

```ts
interface TextLine {
  line: number;

  text: string;

  startOffset: number;
  endOffset: number;
}
```

后续章节定位不要只保存标题字符串。

必须能够精确定位：

```text
character offset
line number
```

---

# 7. Unicode / 全角半角处理

需要谨慎处理。

可以安全标准化：

```text
全角数字 → 半角数字
全角英文 → 半角英文
特殊空格 → 普通空格
异常 Unicode 空白
```

但是：

```text
中文标点
破折号
省略号
书名号
引号
```

不能简单全部转成 ASCII。

小说标点可能携带：

```text
语气
停顿
对话结构
TTS 韵律
```

所以必须保留语义。

---

# 8. 空白处理

规则：

```text
行尾空格删除
连续普通空格按规则处理
超过阈值的连续空行压缩
段落结构保留
```

例如：

```text
10 个连续空行
```

可以压缩成：

```text
2 个换行
```

但是不要：

```text
全文 replace(/\s+/g, " ")
```

因为这会破坏段落。

---

# 9. HTML / EPUB 清洗

EPUB 不能简单：

```text
HTML → textContent
```

必须保留基本语义结构：

```text
heading
paragraph
blockquote
line break
chapter boundary
```

转换为：

```ts
interface DocumentBlock {
  id: string;

  type:
    | "heading"
    | "paragraph"
    | "quote"
    | "separator"
    | "unknown";

  text: string;

  source?: {
    file?: string;
    element?: string;
  };
}
```

EPUB 应优先遵循其：

```text
spine 阅读顺序
```

而不是按照 ZIP 中文件名称排序。

如果 EPUB 自带：

```text
TOC
NAV
NCX
```

则提取为独立的：

```text
tocCandidates
```

用于辅助章节识别。

但不能完全信任目录。

最终仍然需要与正文中的章节位置进行匹配。

---

# 10. Markdown

Markdown 应解析成结构，而不是仅对原字符串使用章节正则。

需要保留：

```text
heading level
paragraph
blockquote
separator
```

例如：

```markdown
# 第一卷

## 第一章 初入江湖
```

应天然形成章节候选。

---

# 11. 噪声文本

需要检测：

```text
网站水印
下载站广告
QQ群
公众号
网址
“本书由 XXX 整理”
“最新章节请访问 XXX”
重复版权信息
重复页眉
重复页脚
```

禁止简单采用一个巨型敏感词列表直接删除。

实现：

```text
Noise Detection
        ↓
Noise Candidate
        ↓
规则判断
        ↓
LLM 判断（必要时）
        ↓
Confirmed Noise
        ↓
程序删除
```

数据结构：

```ts
interface NoiseCandidate {
  id: string;

  text: string;

  occurrenceCount: number;

  positions: TextRange[];

  type:
    | "watermark"
    | "advertisement"
    | "header"
    | "footer"
    | "copyright"
    | "unknown";

  confidence: number;

  action:
    | "remove"
    | "keep"
    | "review";
}
```

如果相同短文本：

```text
在数百章节固定位置反复出现
```

可以提高其作为水印/广告的置信度。

# 12. 章节识别总体设计

章节识别采用：

```text
规则识别
+
文档结构
+
目录信息
+
LLM 语义判断
```

生成唯一：

```text
Chapter Index
```

之后由程序根据索引切分小说。

禁止：

```text
把一本小说发送给 LLM
→
要求 LLM 输出 N 个章节文本
```

正确方式：

```text
小说文本
↓
寻找标题候选
↓
LLM 判断候选是否为章节
↓
生成 offset
↓
程序 slice()
```

# 13. Chapter Candidate

首先扫描全文找到：

```text
可能是章节标题的行
```

例如：

```text
第一章
第1章
第一章 初入江湖

第一回
第十二回 风起

卷一
第一卷
第一卷 七玄门

Chapter 1
Chapter 001
Chapter One

序章
楔子
前言
引子
终章
尾声
番外
后记
```

产生：

```ts
interface ChapterCandidate {
  id: string;

  line: number;

  startOffset: number;
  endOffset: number;

  rawTitle: string;

  normalizedTitle: string;

  rule?: string;

  ruleConfidence: number;

  contextBefore: string[];
  contextAfter: string[];
}
```

# 14. 章节标题规则

至少支持：

```text
第一章
第1章
第一百二十三章
第001章

第一回
第十二回

第一节

Chapter 1
Chapter 12
CHAPTER XII

第一卷
卷一
卷 1

第一卷 第一章
第一卷 第十二章 风起云涌
```

不要只使用：

```regex
/^第.*章$/
```

这种宽泛正则。

章节标题应结合：

```text
标题长度
数字结构
所在行是否独立
前后换行
上下文
重复模式
全文规律
```

综合判断。

# 15. 中文数字解析

实现统一：

```ts
parseOrdinal()
```

支持：

```text
一
十一
二十五
一百零八
一千零二
两百
零一
```

输出：

```ts
{
  raw: "一百零八",
  value: 108
}
```

用于：

```text
章节排序
缺章检测
重复编号检测
卷号解析
```

# 16. 不要混淆卷和章

结构：

```text
Book
 ├─ Volume
 │   ├─ Chapter
 │   ├─ Chapter
 │   └─ Chapter
 └─ Volume
```

例如：

```text
第一卷 修仙之路
第一章 山村
第二章 青牛镇

第二卷 魔道
第一章 重逢
```

这里：

```text
第二卷第一章
```

不能因为 chapterNumber=1 判断为重复章节。

章节唯一 ID 应与顺序位置绑定：

```text
chapter_000001
chapter_000002
```

不要直接使用：

```text
volume_2_chapter_1
```

作为唯一事实来源。

# 17. LLM 辅助章节识别

规则识别不能确认时，调用 LLM。

禁止发送全文。

只发送：

```text
候选标题
候选标题前后若干行
邻近候选标题
当前文档章节规律摘要
```

例如：

```json
{
  "candidate": {
    "text": "风起青萍",
    "line": 18231
  },

  "contextBefore": [
    "……上一段小说内容……"
  ],

  "contextAfter": [
    "韩立缓缓睁开双眼……"
  ],

  "nearbyHeadings": [
    "第三十二章 离去",
    "第三十四章 重逢"
  ]
}
```

LLM 只能返回严格 JSON：

```json
{
  "isChapterHeading": true,
  "type": "chapter",
  "volumeNumber": 1,
  "chapterNumber": 33,
  "title": "风起青萍",
  "confidence": 0.96,
  "reason": "位于第三十二章和第三十四章之间，结构和章节标题一致"
}
```

设置 Schema 校验。

如果 JSON 不符合 Schema：

```text
重试
```

超过次数：

```text
requiresReview
```

不得让错误结果直接进入正式 Chapter Index。

---

# 18. 全书章节模式分析

第一次规则扫描之后，应分析全书标题模式。

例如发现：

```text
93% 标题形式为：

第{number}章 {title}
```

则：

```text
“第三十一章”
```

即使没有副标题，也应获得较高置信度。

而：

```text
“第一章修炼功法”
```

虽然格式异常，也可能需要进一步判断。

建立：

```ts
interface ChapterPatternProfile {
  commonPatterns: ChapterPattern[];

  numberedRatio: number;

  titleLengthRange: [number, number];

  volumePattern?: string;
}
```

后续候选判断应使用全书模式作为上下文。

---

# 19. 生成 Chapter Index

章节识别结束后，先生成索引：

```json
[
  {
    "chapterId": "chapter_000001",

    "order": 1,

    "volume": {
      "order": 1,
      "number": 1,
      "title": "七玄门"
    },

    "chapterNumber": 1,

    "title": "山边小村",

    "heading": "第一章 山边小村",

    "headingStart": 1024,
    "contentStart": 1040,
    "contentEnd": 9842,

    "source": {
      "startLine": 42,
      "endLine": 328
    },

    "confidence": 0.99,

    "detectedBy": [
      "regex",
      "pattern-analysis"
    ]
  }
]
```

核心原则：

```text
先生成索引
再切文本
```

不要在识别过程中立即修改文本。

---

# 20. Chapter Index 校验

生成索引后必须执行：

```text
validateChapterIndex()
```

至少检查：

### Offset

必须满足：

```text
start >= 0
end > start

chapter[i].start < chapter[i+1].start
```

不得出现：

```text
章节重叠
逆序
非法 offset
```

---

# 21. 文本覆盖率校验

章节切分后必须知道：

```text
全文有哪些字符没有归属于任何章节
```

输出：

```ts
interface CoverageReport {
  totalCharacters: number;

  coveredCharacters: number;

  uncoveredCharacters: number;

  coverageRatio: number;

  uncoveredRanges: TextRange[];
}
```

例如：

```text
正文覆盖率：99.82%
```

剩余：

```text
作者介绍
序言
后记
网站广告
```

不能简单丢弃。

必须分类为：

```text
frontMatter
chapter
appendix
noise
unknown
```

# 22. 程序切分章节

Chapter Index 通过校验后：

```ts
sliceChapters(canonicalText, chapterIndex)
```

程序按照：

```text
contentStart
contentEnd
```

进行确定性 slice。

生成：

```ts
interface Chapter {
  id: string;

  order: number;

  volume?: VolumeInfo;

  number?: number;

  title?: string;

  rawHeading?: string;

  rawText: string;

  normalizedText: string;

  sourceRange: TextRange;

  hash: string;

  status:
    | "valid"
    | "warning"
    | "requires_review";
}
```

# 23. 不要使用章节文件作为唯一存储方式

可以为了调试生成：

```text
chapter_000001.txt
chapter_000002.txt
```

但是正式数据模型必须是结构化数据。

推荐：

```text
Novel
 ├── Metadata
 ├── SourceDocument
 ├── Volumes
 ├── Chapters
 ├── Scenes
 ├── Segments
 └── ValidationReports
```

# 24. 重复章节检测

章节切分完成后执行：

```text
detectDuplicateChapters()
```

至少检查三类重复。

---

## 24.1 重复编号

例如：

```text
第38章
第39章
第39章
第40章
```

产生：

```json
{
  "type": "duplicate_number",
  "chapters": [
    "chapter_000039",
    "chapter_000040"
  ]
}
```

注意：

```text
不同卷允许章节编号重新从 1 开始。
```

---

# 25. 重复标题

例如：

```text
第129章 大战
第130章 大战
```

只标记：

```text
warning
```

不能认为一定重复。

小说存在重复标题是合法的。

---

# 26. 重复正文

计算：

```text
exact hash
```

用于发现完全重复。

同时计算：

```text
normalized content fingerprint
```

忽略：

```text
空格
标题
少量网站水印
```

发现近似重复。

例如：

```text
Chapter 100

和

Chapter 101
```

正文相似度：

```text
99.7%
```

则标记：

```text
probable_duplicate_content
```

不要自动删除。

---

# 27. 缺失章节检测

例如：

```text
第10章
第11章
第13章
```

发现：

```text
第12章可能缺失
```

输出：

```ts
interface MissingChapterIssue {
  volume?: number;

  previousChapter: string;
  nextChapter: string;

  expectedNumbers: number[];

  confidence: number;

  reason: string;
}
```

但：

```text
编号不连续 != 一定缺章
```

例如作者可能：

```text
故意跳号
使用特殊章节
章节名没有数字
```

因此这里只产生：

```text
warning
```

必要时交给 LLM 分析。

---

# 28. 缺章的 LLM 二次判断

向 LLM 提供：

```text
上一章标题
上一章结尾
下一章标题
下一章开头
章节编号规律
目录信息
```

让 LLM 判断：

```json
{
  "likelyMissing": true,
  "confidence": 0.91,
  "expectedChapter": 12,
  "reason": "编号从11跳至13，同时上下文存在明显剧情断层"
}
```

LLM 仍然：

```text
只能报告问题
不能自行补写缺失内容
```

绝对禁止自动生成所谓“缺失章节”。

---

# 29. 章节顺序异常

检测：

```text
第100章
第102章
第101章
第103章
```

输出：

```text
chapter_order_anomaly
```

如果正文内容与目录顺序冲突：

```text
保留正文顺序
+
记录目录冲突
```

不要自动重排正文，除非能够获得充分证据。

---

# 30. 超短章节

统计章节字符数。

例如全书：

```text
中位章节长度 = 4200 字
```

某章节：

```text
83 字
```

则检查是否：

```text
错误章节标题
错误切分
章节正文缺失
番外短章
作者公告
```

产生：

```text
suspicious_short_chapter
```

---

# 31. 超长章节

如果某章节长度明显超过整体分布：

```text
例如中位数 4000 字
某章 52000 字
```

优先检查：

```text
是否漏掉了章节标题
```

程序重新扫描该章节内部的：

```text
ChapterCandidate
```

必要时再次调用 LLM。

最终必须生成：


---

# 33. 文本清洗不能与纠错混在一起

本阶段可以处理：

```text
排版问题
广告
网站水印
控制字符
异常空格
重复标题
HTML 残留
```

但是：

```text
错别字
人物姓名错误
词语误用
多音字
语法错误
```

应该进入后续：

```text
Text Correction Pipeline
```

原因：

结构清洗属于：

```text
deterministic transformation
```

而小说纠错属于：

```text
semantic transformation
```

二者必须能够分别审计和回滚。

---

# 34. 删除文本必须记录 Diff

任何删除操作必须记录：

```ts
interface TextEdit {
  id: string;

  type:
    | "remove_noise"
    | "normalize"
    | "remove_duplicate_heading"
    | "other";

  range: TextRange;

  before: string;
  after: string;

  reason: string;

  confidence: number;

  source:
    | "rule"
    | "llm"
    | "manual";
}
```

必须能够回答：

```text
这一段为什么消失了？
是谁判断删除的？
什么时候删除的？
原文是什么？
```

---

# 35. Chapter → Scene → Segment

章节完成后继续进行：

```text
Chapter
 ├─ Scene
 │   ├─ Segment
 │   ├─ Segment
 │   └─ Segment
 └─ Scene
```

不要直接：

```text
Chapter → Chunk
```

Scene 是后续音频制作的重要语义单位。

---

# 36. Scene 定义

Scene 表示：

```text
连续发生的一段叙事场景
```

场景变化通常包括：

```text
时间明显变化
地点变化
叙事视角明显变化
主要人物集合变化
剧情事件切换
梦境 / 回忆开始结束
战斗阶段发生重大切换
明显分隔符
```

例如：

```text
韩立在洞府修炼
        ↓
三日后
        ↓
坊市
```

可以切成两个 Scene。

---

# 37. Scene Candidate

程序首先寻找可能边界：

```text
***
——
三日后
翌日
与此同时
另一边
回到……
夜幕降临
第二天清晨
```

同时分析：

```text
段落结构
时间表达
地点实体变化
主要角色变化
```

形成：

```ts
interface SceneBoundaryCandidate {
  offset: number;

  paragraphIndex: number;

  signals: string[];

  ruleConfidence: number;
}
```

---

# 38. LLM Scene 判断

LLM 输入：

```text
边界前若干段
边界后若干段
```

而不是整章。

返回：

```json
{
  "isSceneBoundary": true,
  "confidence": 0.87,
  "signals": [
    "time_change",
    "location_change"
  ],
  "reason": "叙事从夜间洞府切换到三日后的坊市"
}
```

然后程序根据 offset 切分。

---

# 39. Scene 数据结构

```ts
interface Scene {
  id: string;

  chapterId: string;

  order: number;

  rawText: string;

  normalizedText: string;

  sourceRange: TextRange;

  metadata?: {
    time?: string;

    location?: string[];

    characters?: string[];

    narrativePerspective?: string;
  };

  confidence: number;
}
```

本阶段 metadata 可以不完整。

后续角色分析 Pipeline 可以继续补充。

---

# 40. Scene 不应该过度切分

不要按照：

```text
一个人物说一句话
```

切 Scene。

也不要简单：

```text
每 2000 字一个 Scene
```

Scene 是语义单位。

如果一个战斗场景长达：

```text
8000 字
```

仍然可以是一个 Scene。

文本长度问题交给：

```text
Segment
```

处理。

---

# 41. Segment 定义

Segment 是：

```text
提供给 LLM / TTS / NLP 的技术处理单位
```

它主要解决：

```text
模型上下文限制
TTS 输入长度
任务并发
失败重试
缓存
```

因此：

```text
Scene = semantic boundary
Segment = technical boundary
```

二者不要混淆。

---

# 42. Segment 切分策略

优先级：

```text
段落边界
↓
完整对话边界
↓
句号 / 问号 / 感叹号
↓
其他标点
↓
强制长度
```

禁止直接：

```ts
text.slice(0, 3000)
```

导致：

```text
句子被切成两半
人物台词被切成两半
```

---

# 43. Segment 长度

长度必须配置化：

```ts
interface SegmentConfig {
  targetCharacters: number;
  minCharacters: number;
  maxCharacters: number;
}
```

不要把：

```text
2000
3000
4000
```

硬编码在业务逻辑中。

后续不同模型可以使用不同配置。

---

# 44. Segment 不要复制正文 overlap

正式 Segment：

```text
Segment 1 = A
Segment 2 = B
```

不要：

```text
Segment 1 = ABC
Segment 2 = CDE
```

否则后续 TTS 容易重复朗读。

如果模型需要上下文，单独保存：

```ts
interface SegmentContext {
  contextBefore?: string;
  contextAfter?: string;
}
```

模型调用时：

```text
contextBefore
+
targetSegment
+
contextAfter
```

但真正需要处理的正文仍然只有：

```text
targetSegment
```

---

# 45. Segment 数据结构

```ts
interface Segment {
  id: string;

  chapterId: string;
  sceneId: string;

  order: number;

  text: string;

  sourceRange: TextRange;

  context?: {
    before?: string;
    after?: string;
  };

  stats: {
    characters: number;
    paragraphs: number;
  };

}
```

# 49. LLM 调用必须缓存

LLM 输入计算 hash：

```text
model
promptVersion
input
config
```

生成：

```text
requestHash
```

如果相同请求已经成功：

```text
直接使用缓存
```

这样重新运行 Pipeline 不需要重复产生大量模型费用。

---

# 50. Prompt 必须版本化

例如：

```text
chapter-detection-v1
scene-detection-v1
noise-detection-v1
```

保存：

```ts
{
  promptVersion: "chapter-detection-v1",
  model: "...",
  inputHash: "...",
  output: {}
}
```

避免未来修改 Prompt 后无法解释旧数据的来源。

---

# 51. LLM Confidence

所有语义判断必须包含：

```text
confidence
```

例如：

```text
>= 0.95
自动接受

0.75 ~ 0.95
结合规则判断

< 0.75
requiresReview
```

具体阈值配置化。

不要硬编码到业务逻辑。

---

# 52. Validation 应优先于 AI

例如章节索引：

```text
第一章
第二章
第三章
第四章
```

规则已经高度可靠时：

```text
不要调用 LLM
```

只处理：

```text
无法通过规则明确判断
存在冲突
存在异常
```

的部分。

目标：

```text
减少 Token
减少成本
减少模型误判
提高可重复性
```

# 60. Property Validation

# 64. 第一阶段验收标准

实现完成后，至少满足：

1. 输入一本 TXT/EPUB/Markdown 小说，可以生成统一结构数据。

2. 原始文件和 rawText 永远不会被覆盖。

3. 章节识别采用：

```text
Rule First
LLM Fallback
```

4. LLM 只负责判断章节边界，不直接生成切分后的小说正文。

5. Chapter Index 包含准确：

```text
order
title
volume
chapterNumber
offset
line
confidence
```

6. 程序根据 offset 确定性生成 Chapter。

7. 系统能够发现：

```text
重复章节编号
疑似重复正文
章节编号缺失
章节乱序
异常短章
异常长章
未覆盖文本
```

8. 每个问题都有：

```text
type
location
evidence
confidence
```

9. Chapter 能继续拆分：

```text
Chapter → Scene → Segment
```

10. Segment 拼接后不得丢字或重复正文。

11. 所有文本修改可以追踪。

12. Pipeline 任意阶段失败后可以重试，而不必从头处理。
